# Changelog

Fork-specific changes on top of stablyai/orca. Format: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Changed

- Plugin inventory (`claudePlugins.inventory`), four assumptions measured against Claude Code 2.1.332 (`--plugin-dir`, init message of `stream-json`): (1) a linked skill folder (symlink, on Windows a junction) loads, so the inventory now follows links when listing skills, agents and commands (before, a Dirent reported a link as neither folder nor file and it was missing; a dangling link is ignored; WSL already followed links). Agent file links could not be created without privilege on the Windows test host; they use the same code path and a test covers them where links are allowed. (2) A skill is named by its folder, never by `name` in the SKILL.md frontmatter; an agent by its frontmatter `name`, a command by its file name: all three already matched. (3) `.mcp.json` in the plugin root is read in addition to `mcpServers` in the manifest (inline object or path); before, a manifest declaration hid `.mcp.json`. (4) The cache key is the raw `cwd` string (`C:\x` and `c:\x` are two entries) and an entry lives 30 s; a changed `enabledPlugins` shows after that or with `refresh: true`. That is by design and stays; the CLI itself reads the settings anew at each start.
- Plugin inventory (`claudePlugins.inventory`): a plugin of a directory marketplace (`known_marketplaces.json`, `source: directory`) is now read from its source folder named in the marketplace's `marketplace.json` (`./<path>` entries), as `claude plugin list --json` reports it (`readFromFolder`), not from the install-cache copy; the cache copy stays the fallback. A synced plugin switched off in any settings layer (`enabledPlugins['<name>@synced']: false`) shows as disabled; confirmed against the CLI, with a test.
- Automation precheck result: exit code `1` skips the run (`skipped_precheck`) and shows the first line the command printed as the reason; every other non-zero exit code, an error or a timeout now fails the run (`dispatch_failed`). Before, exit codes 2 and up were also recorded as skipped, so a broken precheck script now shows up as a failure instead of a quiet skip.
- Run now and `orca automations run` run the precheck too (before, only scheduled runs did). Event runs still skip it.
- A run of an automation on an existing workspace folder waits (stays queued) while another run on the same folder is starting or running, and starts when that run ends.
- Agent profile runs are matched to their Claude session by session id instead of working folder and 10-minute window: `runs.json` records the pane (`paneKey`) at the start and the pane's first hook event pins the run to the Claude session id (`sessionId`), so a resumed session is matched too. A start that no hook event ever reported stays unmatched; records written before this change keep the old folder and window match.

### Added

- Automation editor: an "Agent profile" picker (below the agent) chooses a profile from the catalog (`app.getAgentProfileCatalog`) or clears it; the choice is saved as `agentProfileId` and shown again when the automation is edited. Offered only for a Claude terminal run without a bot or session reuse; if the setup changes so a chosen profile no longer applies, the editor says so and saving removes it. Central profiles are not listed yet because runs resolve only profiles in settings. A host move keeps the saved profile.
- `claudePlugins.inventory` now answers for WSL workspaces: when `cwd` (or the workspace's folder) or `accountHomePath` is a UNC path of a distro (`\\wsl.localhost\<distro>\...`), the config folder, plugin folders, `.mcp.json` and org-synced plugins are read inside that distro (default account: the distro user's `~/.claude`; `$CLAUDE_CONFIG_DIR` of the distro's shell is not consulted). The result carries `wslDistro`, and `configDir`, `cwd` and every `installPath` are the distro's Linux paths. A stopped distro is not started (the call fails instead). A workspace in a distro combined with a Windows account folder, or the reverse or another distro, is refused. SSH workspaces stay refused (`skills.discover` does the same): the remote home is not reachable from this host without a relay call. `claudePlugins.weights` stays unavailable for WSL, because the host's `claude` CLI measures it. In a WSL plugin, an agent file the manifest declares outside an `agents/` folder is named by its file name, not its frontmatter.
- Automation runs hold while the agent's account (Claude or Codex) has used up a usage window: the run stays queued until the reset and starts then. Desktop only; a run held this way is not carried across an Orca restart.
- `orca vm env doctor` gains a `workstation` check group driven by a JSON target list (`--requirements`, `$ORCA_WORKSTATION_REQUIREMENTS`, or `~/.orca/workstation-requirements.json`; no file, no group): commands with minimum version, Claude marketplaces and plugins, PATH entries, each reported `pass` / `fail` / `skip` (not verifiable). Foreign hooks in `~/.claude/settings.json` show up as `info`. `--fix <check-id>` runs only allowlisted repairs (`claude plugin install`, `claude plugin marketplace add`, `npm install -g`, `dotnet tool install`). Format: [docs/workstation-requirements.md](docs/workstation-requirements.md). The GUI button is the next entry.
- VM build sheet: when the environment checks fail, each check that has an allowlisted repair shows a Fix button with the command it will run; on success the checks run again. New RPC method `environment.doctor.fix` (params `path`, `checkId`; capability `environment.doctor.fix.v1`): the VM's server looks the check up in its own target list and re-validates the argv against the allowlist, so a client can never send a command. An older VM server shows a note instead of the button working.
- `config/scripts/local-fork/start-local-fork.ps1`: builds the fork from the checkout and starts it on Windows (`-Mode Dev` or `-Mode Packaged`).
- RPC method `claudePlugins.inventory`: lists the Claude plugins of an account (`accountHomePath`, default the host's) for a workspace (`worktreeId` or `cwd`), each with scope, enabled state, version, declared dependencies, skills, agents, commands and MCP servers, plus the workspace's `.mcp.json` servers. Org-synced plugins (`<name>@synced`) are included. Read from config files and plugin folders, cached for 30 s. WSL workspaces are read inside the distro (see the first entry); SSH workspaces are refused on purpose.
- Agent profiles (`agentProfiles` setting, Claude): a terminal start can apply a saved profile (`agentProfileId` on `launchAgentInNewTab`). The start plan adds the profile's `--settings`, `--mcp-config`, `--model`, permission and tool flags before the other launch args, so an explicit model or permission pick still wins; main writes the profile files under `<userData>/agent-profiles/<id>/` right before the PTY spawns. Refused, not silently dropped: non-Claude agents, SSH/WSL/web hosts, chats, prompts that wait for the agent, profiles with `accountId`, unknown ids. No picker or editor yet.
- Automations can start with an agent profile: `agentProfileId` on an automation (CLI `orca automations create|edit --agent-profile <id>`, `--agent-profile=` clears; capability `automations.agent-profile.v1`). Each fresh run of a Claude terminal automation writes the profile files and starts the agent with the profile's arguments, for a new workspace per run and an existing one. A run whose target cannot carry the profile (remote host, WSL, chat surface, Claude-account profile, missing profile, failed preflight) fails with the reason instead of starting without it; saving refuses non-Claude agents, chat, bots and session reuse. A profile makes a plugin-created automation count as elevated. The editor picks it (see the entry above); central profiles are not resolved for runs yet (only profiles in settings).
- Agent profile preflight: before a profile start, main checks the profile against this machine (plugin installed and its folder present, `--plugin-dir` exists, MCP server definition, startup script on disk, credential variables set (name only, a warning), tool names only on servers inside the strict MCP scope, `--agent` resolvable, managed `disableSideloadFlags` from `managed-settings.json`, `managed-settings.d` and the Windows HKLM/HKCU `Settings` policy). Errors block the start with the findings as the spawn error; the check reads inventory and files only (no network). IPC `app:preflightAgentProfile` / `window.api.app.preflightAgentProfile` returns the findings for a picker. The real MCP connection test stays separate. Not yet checked: macOS plist policy, `--agent` at spawn (the profile has no agent field yet).
- Agent profiles, central and default: setting `agentProfileCentralDir` points at a folder of `*.json` profiles that Orca only reads, never writes; they are read-only and win over a local profile of the same id (the local one stays untouched). Orca warns when group or others can write to the folder (not checked on Windows) and skips invalid or duplicate files. Bundled default profiles (`orca-plan`, `orca-review`) are copied once into `agentProfiles`; a copy that still equals what was copied while the template changed is classified `outdated`, a changed copy `edited`. IPC `app:getAgentProfileCatalog` lists origin, read-only flag and state per profile; `app:resetDefaultAgentProfile` restores the template and keeps an edited copy as `<id>-edited`. Launches resolve central profiles too. No picker or editor UI yet.
- Profile context weight: RPC method `claudePlugins.weights` (same params as `claudePlugins.inventory`) returns the plugin inventory plus each plugin's always-on tokens, measured in the background with `claude plugin details` (concurrency 2, cached per plugin id, version and folder, 60 s pause after a failure). It answers from the cache at once and lists unmeasured plugins as `pending`, so a picker never waits. `weighProfileContext` (`src/shared/agent-profile`) turns inventory, measurements and a profile into a measured share (plugins; org-synced plugins stay loaded and are marked locked) and an estimated share (a flat 3000 tokens per MCP server, since the CLI does not count tool schemas), recomputed without a new start when a switch changes. No editor or picker UI yet (the profile editor is #15 part 2).
- Agent profile runs in Stats & Usage (Claude): each profile terminal start is recorded in `<userData>/agent-profiles/runs.json` with the profile's intent (plugins, MCP servers, model, org-synced plugins). Usage tracking matches it to its Claude session (see the session-id entry under Changed) and shows, per run, Soll against Ist (plugins and MCP servers from the transcript's skill/agent/tool listings or a stream init frame; org-synced plugins listed apart; a log without listing is "not determinable", never empty), used tools, skills and subagents, and what was offered but never used. Per profile: runs and median tokens (USD is only a sum, not comparable). New usage call `claudeUsage:getProfileLoadout`.
- `start.ps1`: one-click entry point that activates Node 24 (fnm), pnpm and the VS C++ build environment, then calls `start-local-fork.ps1`.
- Profile chip in the terminal pane header: a pane whose agent was started from a profile shows the profile name. Main keeps the binding pane to run (`app:getAgentProfilePaneBindings`); a later start without a profile in the same pane, or a different Claude session reported by it, removes the chip. Appears at the latest with the first hook event.
